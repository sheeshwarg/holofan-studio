# Findings

- **fnd_1** The original talks TCP to 192.168.4.1:20320 (fn 0x4019e0). After connecting it must send the hello "C0EEB7C9BAA3C0EEBDF9E5B7" (0x408920). Each command is framed "C0EEB7C9BAA3" + 3 length bytes [L/323, 0x63+(L/17)%19, 0x62+L%17] + payload + "C0EEBDF9E5B7" (0x408a80). On/Off is the 1-byte payload 'a' (button 1066 -> 0x404c10); the old rebuild sent plain text "POWER", so the fan ignored it and dropped the link. (Worked it out; evidence: ev_17f66c60bc1453718d34b54ff4375c485e2f31195ec58403e5595aa4125b5098, ev_fcfdd67e45fe435670229718694a56e8a2a1d465b005bbb1d2d12d4618fbdc34, ev_5197dc37257cc4d8ce1a9c9870fc4f8458cb7b6905666367b9d88d722dff1037, ev_a68b895426074e86b7480a0f89a46c253e966173e1c923f3710ac67cb61678bd, ev_fa65d9eaeb8e428119f0ac0919bfd5bf10b28ea8ea4b8d33ff06f0ad03e1d023)
- **fnd_2** Live test against the person's fan at 192.168.4.1:20320: with the hello the fan kept the TCP connection open for 60 s and sent 4 status frames by itself; without the hello it closed the connection after 1.6 s. The rebuild now reads the fan's real status (model 42-F2, 1 file, sleeping). This explains the reported constant disconnects. (Seen it; evidence: ev_a68b895426074e86b7480a0f89a46c253e966173e1c923f3710ac67cb61678bd, ev_fcfdd67e45fe435670229718694a56e8a2a1d465b005bbb1d2d12d4618fbdc34)
- **fnd_3** The .BIN format comes from 0x405dc0/0x402b60: linearPolar unwrap into rows×LEDs RGB (42-F2: 512×112, 6-bit, 129024 bytes/frame, 12 fps), a colour curve per decoding mode, hub thinning, bit planes and a 42-F2 bit interleave. The rebuild's decoder turns a frame of the person's 4Tiger.BIN into the tiger, and re-packing it gives identical bytes. Brightness 'l'/'m' changed the live fan between medium and low; the app's bug was the fake 10-step scale and back-to-back command bursts. (Seen it; evidence: ev_61feb109484585ef7e9fb084f75dcc1959ada54fee4697ccf7b18032d34bed56, ev_8211b608f4d9c19b5a580ccd41fd7c275e7a737d84d569a42ecb961c9d565485)
